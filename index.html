Inside the internship

Measure the phase. Find the boundary.

Beyond headline throughput: workload characterization, capacity estimates, parallelism trade-offs, and the shared state that can make an otherwise identical run behave differently.

01

Prefill and Decode, measured separately

I built phase-isolated workload sweeps on an eight-GPU B300 node, separating long-prompt admission and batching from token-step execution. Throughput, tail latency, completion, and correctness were tracked separately rather than collapsed into one score.

How a performance anomaly became a routing-state investigation

Repeated Prefill runs exposed intermittent low-throughput behavior. I isolated generation-health traffic as a trigger, then traced how health dispatch mutated the Data Parallel Controller state also used by user requests. A patched/unpatched × health-on/off comparison made the causal test explicit. The fix, merged into SGLang main on 11 October 2026, separates health routing and load-budget bookkeeping from user dispatch.

Public A/B evidence and merged fix · PR #35721 ↗
02

Estimate before the full-node test

Extended an InferFlux-based capacity model for the target model and B300 topology. Model structure, compute and bandwidth limits, KV memory, sequence lengths, parallel layout, and efficiency priors produce a plausible Prefill/Decode envelope before a full load test.

The output is a capacity estimate, not a guaranteed throughput number. Gaps between prediction and measurement help prioritize memory, communication, batching, or runtime investigation.

03

Parallelism is a workload decision

Compared DP Attention and context parallelism (CP) across concurrency regimes, and examined expert placement and load-balancing (EPLB) costs. A layout that lowers isolated-request latency can still lose at higher concurrency; redistribution and redundant experts also consume time and memory.

Static expert placement and dynamic rebalancing are separate decisions. I treat low-return settings and rollbacks as experimental evidence; comparisons require aligned workloads, harnesses, and resource budgets.

01 · MODEL × SYSTEM

MiniCPM-o 4.5 on NVIDIA B300 and Ascend 910C ↗

Built a training-to-runtime path: B300 draft-model training, DSpark speculative execution, draft-aware GGUF conversion, and Ascend 910C deployment. Profiling guided kernel and graph changes. On the same 120-second duplex video and local harness, Core real-time factor (RTF) fell 0.6754 → 0.4829 (about 28.5% lower). Training acceptance, operator launches, and duplex RTF are separate evidence endpoints.

What changed in the final duplex configuration?

The final stack also reduced visual input from overview + slice to overview only, and increased the first TTS chunk from 5 to 10 tokens. The latter trades about +100 ms first-response latency for less repeated boundary work. Four finite submission checks passed; this does not establish broad visual-quality equivalence.

Thinker-side speculation was disabled in the final short-chunk duplex configuration because its overhead worsened RTF. Draft-model acceptance and separate text-workload acceleration remain independent deliverables, not explanations for the final duplex gain.

02 · ROUTING STATE

DP health checks: independent routing-state repair ↗

Independently traced intermittent Prefill throughput drops to generation-health requests changing shared user-routing state. Designed the patched/unpatched × health-on/off comparison, implemented separate health routing and load-budget handling, and added regression tests. My PR #35721 merged into SGLang main. On the tested eight-GPU B300 workload, all four patched health-on runs recovered the expected throughput range.

Mechanism, validation, and contribution

A health request could mutate DPC dispatch state before being skipped by a busy scheduler. I isolated health round-robin and user load-budget state while preserving explicit rank and PD routing semantics. The work added 23 CPU tests initially; the rebased test file passed 30 tests. B300 performance evidence predates the rebase.

Long-term research lens

Systems for model-centric workloads

What interests me is not one serving framework, but how systems abstractions, resource management, and execution mechanisms should evolve when models become a dominant computational workload.

How can inference systems adapt to changing workloads while preserving correctness and predictable latency?

Research interest — adaptive inference systems. Real serving workloads are non-stationary: request arrivals, sequence lengths, Prefill/Decode ratio, modality, SLO, cache pressure, and hardware availability can change over time. I want to study how measured workload behavior can inform online runtime decisions, including the cost of changing policy and a reliable fallback.

01

Observe

Workload phase, arrival pattern, sequence distribution, cache pressure, SLO, telemetry, and resource availability.

02

Model

Estimate how workload × hardware × policy maps to throughput, latency, memory use, and switching cost.

03

Adapt

Change one or two high-impact decisions first: batching, cache policy, parallel layout, or execution strategy.

04

Validate

Require runtime invariants, safe fallback, controlled regression, and long-run stability — not performance alone.

An open direction, grounded in experiments: begin with one workload family, a small hardware set, and one or two runtime decisions. Kernel fusion, graph/draft memory, and multimodal streaming offer concrete cases; each needs its own bottleneck evidence and correctness contract before a broader claim.
