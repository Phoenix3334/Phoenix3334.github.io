How a performance anomaly became a routing-state investigation

Repeated Prefill runs exposed intermittent low-throughput behavior. I isolated generation-health traffic as a trigger, then traced how health dispatch mutated the Data Parallel Controller state also used by user requests. A patched/unpatched × health-on/off comparison made the causal test explicit. The fix, merged into SGLang main on 11 October 2026, separates health routing and load-budget bookkeeping from user dispatch.

02

Estimate before the full-node test

Extended an InferFlux-based capacity model for long-context inference and used workload, compute/bandwidth limits, cache memory, parallel layout, and efficiency priors to narrow the test space. For Kimi K3, examined DCP and the capacity/rollback boundaries of KV and SSM state pools.

The output is a capacity estimate, not a guaranteed throughput number. Gaps between prediction and measurement help prioritize memory, communication, batching, or runtime investigation.

03

Parallelism is a workload decision

Compared DP Attention and context parallelism across load regimes. In a separate CP8 low-latency configuration on GB300, median TTFT was 0.666 s at 60k and 1.516 s at 128k input, each with one output token. These are separate operating points from the high-throughput Prefill rows.

Peak capacity, peak throughput, and minimum latency are different objectives. Version upgrades and larger batches are evaluated per workload rather than assumed to improve every case.

04

EPLB: measure balance, then test throughput

Investigated DeepSeek-V4-Pro Prefill imbalance on a single eight-GPU B300 node with SGLang/MegaMoE. I compared expert placement and rebalancing, recorded expert loads, and profiled execution and communication. The investigation separated logical expert popularity, physical placement and replica dispatch, kernel block rounding, and request-supply gaps, so a better token-count balance would not be mistaken for an end-to-end speedup.

Result: a placement-only experiment improved physical-rank token balance while logical expert counts stayed unchanged. It used no extra expert replicas. Clean held-out validation remains incomplete, so I claim no validated throughput gain or limit on EPLB's potential.

What the experiment changed about the next step

Earlier request-path confounds prevented a clean end-to-end conclusion. CPU top-k also failed to reproduce GPU routing reliably near ties, so bias perturbations were not established as safe optimizations. I proposed a serving-level production-versus-synthetic-balanced routing comparison in SGLang, and asked DeepSeek about placement, replica-aware cost models, and the boundary with model-level routing. These are open proposals; a synthetic balanced result would be a profiling reference, not a quality-preserving optimization.

05

Component baselines and local kernel optimization

Designed MegaMoE tests across model shapes, batch/token counts, and fast-math settings, using nsys/NCU to analyze compute, memory, and communication. The fused chain measured 1.51–1.87× against the original FFN path; a separate small-batch point reached about 5.1 TB/s HBM bandwidth. June component baselines informed independently designed September EPLB retests and serving-level comparisons.

Implemented inverse-RoPE + FP8 quantization fusion in the CUDA attention path. The earlier SGLang 0.5.17-derived B300 comparison measured +1.63% input throughput at 60k input / 1 output token, with FP8 codes and scales byte-identical in numerical tests. The public upstream port is PR #43786 ↗.

Component speedups and HBM points are separate from whole-model gains. MegaMoE is an upstream implementation; my contribution is test design, profiling, and integration analysis. PR #43786 is open; the reported GPU measurements predate its cleanup refactor, which still needs updated GPU validation. The fusion result is not added to the AR-to-EAGLE gain.

MiniCPM-o 4.5 on NVIDIA B300 and Ascend 910C ↗

Built a training-to-runtime path: B300 draft-model training, DSpark speculative execution, draft-aware GGUF conversion, and Ascend 910C deployment. Profiling guided kernel and graph changes. On the same 120-second duplex video and local harness, Core real-time factor (RTF) fell 0.6754 → 0.4829 (about 28.5% lower). Training acceptance, operator launches, and duplex RTF are separate evidence endpoints.

What changed in the final duplex configuration?

The final stack also reduced visual input from overview + slice to overview only, and increased the first TTS chunk from 5 to 10 tokens. The latter trades about +100 ms first-response latency for less repeated boundary work. Four finite submission checks passed; this does not establish broad visual-quality equivalence.

Thinker-side speculation was disabled in the final short-chunk duplex configuration because its overhead worsened RTF. Draft-model acceptance and separate text-workload acceleration remain independent deliverables, not explanations for the final duplex gain.

02 · ROUTING STATE

DP health checks: independent routing-state repair ↗

Independently traced intermittent Prefill throughput drops to generation-health requests changing shared user-routing state. Designed the patched/unpatched × health-on/off comparison, implemented separate health routing and load-budget handling, and added regression tests. My PR #35721 merged into SGLang main and is listed in the v0.5.22 release notes under Parallelism & Disaggregation. On the tested eight-GPU B300 workload, all four patched health-on runs recovered the expected throughput range.

Mechanism, validation, and contribution

A health request could mutate DPC dispatch state before being skipped by a busy scheduler. I isolated health round-robin and user load-budget state while preserving explicit rank and PD routing semantics. The work added 23 CPU tests initially; the rebased test file passed 30 tests. B300 performance evidence predates the rebase.

Long-term research lens

Systems for model-centric workloads

What interests me is not one serving framework, but how systems abstractions, resource management, and execution mechanisms should evolve when models become a dominant computational workload.

How can inference systems adapt to changing workloads while preserving correctness and predictable latency?

Research interest — adaptive inference systems. Real serving workloads are non-stationary: request arrivals, sequence lengths, Prefill/Decode ratio, modality, SLO, cache pressure, and hardware availability can change over time. I want to study how measured workload behavior can inform online runtime decisions, including the cost of changing policy and a reliable fallback.

01

Observe

Workload phase, arrival pattern, sequence distribution, cache pressure, SLO, telemetry, and resource availability.

02

Model

Estimate how workload × hardware × policy maps to throughput, latency, memory use, and switching cost.

03

Adapt

Change one or two high-impact decisions first: batching, cache policy, parallel layout, or execution strategy.

04

Validate

Require runtime invariants, safe fallback, controlled regression, and long-run stability — not performance alone.

An open direction, grounded in experiments: begin with one workload family, a small hardware set, and one or two runtime decisions. Kernel fusion, graph/draft memory, and multimodal streaming offer concrete cases; each needs its own bottleneck evidence and correctness contract before a broader claim.
