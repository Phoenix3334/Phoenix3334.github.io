01 · PIPELINE / STREAM LIFETIME

PP output corruption: repair tensor lifetime across CUDA streams ↗

Kimi-K3 produced long token-0 runs when I deepened the asynchronous PP Decode queue. I traced the failure to receive buffers being reused before the forward stream read them. After fixing tensor lifetime, affected requests fell from 51/192 and 98/192 to 0/192 at depths 2 and 3. PR #47614 merged on 2 November 2026.

Expand the investigation: reproduction, checksum evidence and the fix

1. Turn an apparent speedup into a correctness test. Deeper asynchronous PP queues appeared faster, but many Kimi-K3 requests emitted long runs of token 0. On PP2 × TP4, depth 1 produced no affected requests in the tested run. Raising the depth to 2 or 3 made the fault reproducible. Synchronizing after each launch also suppressed it, which directed the investigation to queued work and tensor lifetime.

2. Measure where the data changed. On the downstream stage, I checked the same proxy tensors just after receive on the communication stream and just before use on the forward stream. Two depth-2 runs had 76/7,498 and 378/7,498 checksum mismatches. Keeping the previous tensor reference alive until the next receive had allocated its buffers gave 0/7,499 mismatches with a similar observed queue depth. Checksum and reference-lifetime controls ↗

3. Extend storage lifetime at the shared launch boundary. CPU scheduling could drop the old reference while a forward-stream read was still queued. The next receive could reuse the same storage and overwrite that microbatch's activations. In _pp_launch_batch, I used record_stream(self.forward_stream) on each non-CPU proxy tensor before run_batch. This tells the allocator to retain storage until forward-stream use completes. Existing stream dependencies still determine execution order.

02 · ROUTING STATE

DP Health: tracing an intermittent Prefill regression ↗

Repeated DeepSeek-V4-Pro Prefill runs on 8×B300 showed intermittent throughput drops. I traced the trigger to generation-health requests changing shared DPC user-routing state before scheduler admission. After isolating health dispatch, all four patched health-ON runs reached 94.56–94.70k input tok/s. PR #35721 shipped in v0.5.22.

Expand the investigation: hypotheses, traces and 2×2 validation

1. Separate scheduling from GPU execution. Identical long-Prefill runs intermittently dropped throughput. I first tested DP Attention, chunk sizing and PrefillDelayer because LOW runs showed rank progress gaps and sustained mixed/delay activity. A Delayer admission-order backport still produced both GOOD and LOW, so I investigated whether a rank received less work or took longer to execute it. Backport counterexample ↗

2. Check whether observation perturbs the run. A continuous alternating 4 OFF / 4 ON DeviceTimer test gave healthy-state means of 94,563 and 94,569 input tok/s. The sample was too small to settle LOW entry probability. Moving from 5 s to 250 ms metrics sampling separated observed chunk completions, and a benchmark start marker made the fast window cover the onset. DeviceTimer A/B ↗

3. Trace the request across the control plane. Client POST, tokenizer, DataParallelController and scheduler admission traces exposed a hidden ordering: a generation-health request could advance shared user round-robin or touch load-budget state before a busy scheduler skipped it. The patch isolated health dispatch and preserved explicit-rank and P/D routing. The initial symptom report was filed on 18 August and the patch opened on 20 August. Health trigger evidence ↗

4. Isolate the cause with a 2×2. On 26 August I held the image, workload, DP Attention, PrefillDelayer and external GET /health polling fixed. Each round started a fresh server and varied only the patch and generation-health request creation. Four-arm experiment ↗

03 · INVESTIGATION / REVIEW

DSpark correctness: from first report to final-fix validation ↗

From July to August, I reported DSpark replay and startup failures, built targeted reproductions, and contributed experiments to the final planner fix. My technical review on PR #32467 validated the no-init variant with a controlled kernel comparison: 13,111/30,000 out-of-bounds plans → 0/30,000.

Expand the investigation: original reports, isolation and regression coverage

1. Follow the failure across replay and startup. On 13 July I filed #31023 for a TP8 compact target-verify replay failure, then opened diagnostic #31455 to bisect synchronization and observe graph metadata. In August I filed #33356 for an independent startup-capture reproducer on v0.5.16. The surfacing rank, shape and kernel varied, so I traced the inputs to those kernels back to their producer.

2. Separate TP agreement, capture ordering and invalid plans. After #31195, all 120/120 TP8 trials agreed on verify budget, lengths and graph key. A separate four-arm startup experiment compared planner patch #32467 and capture-ordering patch #33795. Full capture succeeded in 0/7 without either, 1/6 with capture ordering alone, and 3/3 with the planner patch alone or both. Each successful planner-patch run captured all 35 shapes. Startup matrix ↗

3. Observe the bad index at the producer and test the proposed fix. A single-GPU reproducer called the real GPU-input planner and checked max(valid ragged_id) < sum(extend_lens). Redundant initialization of shared warp scratch could overwrite another warp's reduction, misclassifying ragged input as uniform. One bad plan reached index 383 for only 360 valid rows. I tested DarkSharpness’s no-init suggestion in the same session, with isolated JIT caches and 30,000 calls per variant. Under the existing 32-warp launch, each warp writes its slot before the existing post-reduction barrier.

05 · DISTRIBUTED COMMUNICATION

GB300 DCP: corrupted Decode outputs and the upstream NCCL guard ↗

I reproduced degenerate Kimi-K3 outputs in graph-captured DCP a2a on two-node GB300. Disabling NCCL Graph Registration reduced degenerate outputs from 12/12 to 0/12 in the local probe. Upstream #43216, authored by zhihengy, introduced a broader default guard that covers this configuration.

Expand the investigation: local A/B, upstream guard and closure

Local diagnosis and alternatives. In the original TP8/DCP8 2×2 probe, only registration ON with temporary exchange buffers produced degenerate outputs. The startup guard in #45371 also completed 640/640 requests in a separate local C128 run. Persistent buffers (#45824) passed an early smoke test, but the no-guard configuration later produced 0/10 valid answers under load in a separate TP8/attention-DP2/DCP4 deployment. I withdrew the apparent speedups and closed that proposal unmerged.

Upstream resolution. #43216 was merged on 22 October 2026. When a deployment spans multiple TP, EP or DP ranks and any CUDA Graph phase is enabled, it defaults NCCL_GRAPH_REGISTER to 0, preserving explicit overrides. The original graph-enabled GB300 DCP a2a configuration meets those conditions, so I closed the narrower #45371 unmerged and marked Issue #45367 completed.

Closure is based on source-level coverage of the original configuration and the earlier local experiments. A matched GB300 end-to-end rerun on current main remains outstanding, and the precise NCCL replay-time mechanism remains unconfirmed.

Estimate before the full-node test

Extended an InferFlux-based capacity model for long-context inference and used workload, compute/bandwidth limits, cache memory, parallel layout, and efficiency priors to narrow the test space. For Kimi K3, examined DCP and the capacity/rollback boundaries of KV and SSM state pools.

The output is a capacity estimate, not a guaranteed throughput number. Gaps between prediction and measurement help prioritize memory, communication, batching, or runtime investigation.

Performance → capacity → economics

Hardware selection, P/D sizing
and deployment economics

Compare serving performance, resource utilization and deployment cost under a defined SLO. Use measured phase capacity for an initial P/D allocation, then validate the combined service path.

01 / SLO

Find the feasible operating point

Sweep concurrency and configuration on the target request mix. Compare TTFT, TPOT, request throughput, memory pressure, failures, and output correctness. Select an operating point that meets the specified latency, quality, and stability criteria.

q_instance = measured requests/s
at the qualifying configuration

Prefill input tok/s, Decode output tok/s, and requests/s describe different quantities. Request lengths and phase balance must stay explicit.

02 / CAPACITY

Size Prefill and Decode separately

Convert Prefill and Decode rates to per-instance requests/s under the same workload and SLO. Size both stages for peak demand, with headroom and redundancy for the deployment.

N_P = ceil(λ_peak / q_P)
N_D = ceil(λ_peak / q_D)
Minimum GPU count = N_P × g_P + N_D × g_D

Validate the resulting P/D ratio with real KV transfers, queueing and end-to-end TTFT/TPOT. Stage-isolated rates are sizing inputs.

03 / TCO

Price delivered service

Use one accounting period for compute rental or hardware depreciation, power, networking, software, and operations. Divide by the correctly delivered token volume under the chosen service criteria. Treat input and output separately when the accounting requires it.

Cost per 1M valid tokens
= period cost / valid tokens delivered × 10⁶

Utilisation, idle reserve, uptime, retries, and traffic shape affect unit cost. Rental and depreciation require a consistent accounting boundary.

Evidence for sizing comes from benchmarks, resource limits and runtime validation. These inputs support hardware selection and comparative cost scenarios. Full TCO requires actual prices, power, utilization, redundancy, operations and delivered traffic.

Inference engineering practice

Measure the service.
Explain the bottleneck.

A repeatable loop across SGLang, NVIDIA GPUs, and Ascend: make the workload and execution path explicit, prove the result, then use it to make a resource decision.

How much correct, reliable serving capacity can this configuration deliver within its latency and resource budget?

01

Deploy & define

Pin model and framework versions, topology, request distribution, cache policy, precision, and resource limits. Confirm the intended backend and communication path.

02

Measure & profile

Separate P/D tests from end-to-end service tests. Use nsys for critical paths, CPU/GPU gaps, communication overlap, synchronisation, and graph coverage; use ncu for selected kernels.

03

Repair & validate

Test one causal hypothesis at a time. Check output quality, failure behaviour, memory boundaries, repeatability, and throughput/latency together. Carry the regression upstream.

04

Size & account

Use qualifying serving capacity for instance sizing, GPU allocation, and cost scenarios. Keep measured results, estimates, and unvalidated assumptions visible.

AI Infra is the connecting layer: model behaviour and workload shape meet runtime scheduling, cache state, kernels, interconnect, and deployment economics. My focus is building and validating that connection.
