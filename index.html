01 · PIPELINE / STREAM LIFETIME

PP output corruption: repair tensor lifetime across CUDA streams ↗

Traced repeated token-0 output at deeper pipeline queues to received tensors being recycled before queued forward-stream reads completed. Checksum probes caught the data changing between receive and forward. I implemented the shared PP launch-boundary repair with record_stream(self.forward_stream); my PR #47614 merged on 2 November 2026.

From a suspicious benchmark to an allocator-lifetime fix

The apparent throughput gain at deeper PP queues came with corrupted outputs. On Kimi-K3, eight B300 GPUs, v0.5.22 and fake PD transfer, PP2 × TP4 at depths 2 and 3 produced 51/192 and 98/192 requests with at least 20 consecutive token 0; patched runs produced 0/192 at both depths. Tests also covered PP4 and a DCP combination. Recording the forward stream keeps the allocator from reusing the tensor storage until that stream finishes reading it.

The B300 reproduction used v0.5.22 and fake transfer, not real two-node PD. GPU results are tied to the documented patch variants. This is a correctness repair; corrupted baseline throughput is not a valid performance comparison.

02 · ROUTING STATE

DP health checks: independent routing-state repair ↗

Independently traced intermittent Prefill throughput drops to generation-health requests changing shared user-routing state. Designed the patched/unpatched × health-on/off comparison, implemented separate health routing and load-budget handling, and added regression tests. My PR #35721 merged into SGLang main and is listed in the v0.5.22 release notes under Parallelism & Disaggregation. On the tested eight-GPU B300 workload, all four patched health-on runs recovered the expected throughput range.

Mechanism, validation, and contribution

A health request could mutate DPC dispatch state before being skipped by a busy scheduler. I isolated health round-robin and user load-budget state while preserving explicit rank and PD routing semantics. The work added 23 CPU tests initially; the rebased test file passed 30 tests. B300 performance evidence predates the rebase.

Investigated corrupted Kimi K3 output in graph-captured DCP all-to-all on two-node GB300. Tested a registration guard (#45371) and persistent buffers (#45824) as alternatives. Both proposals closed unmerged. The issue retains the controlled evidence.

Validation scope of the two proposals

The persistent-buffer PR head 9cb1de5 completed the two-node 12-prompt probe with 12/12 correct outputs and no degenerate outputs, with registration enabled and the startup guard absent. Focused DCP regression tests passed: 23 tests plus 5 subtests. The guard policy also completed a separate 640/640-request run on the previously failing deployment; that result is not validation of its later merge-updated head.

The PRs are alternatives for one failure, not two fixes to stack. How a performance anomaly became a routing-state investigation

Repeated Prefill runs exposed intermittent low-throughput behavior. I isolated generation-health traffic as a trigger, then traced how health dispatch mutated the Data Parallel Controller state also used by user requests. A patched/unpatched × health-on/off comparison made the causal test explicit. The fix, merged into SGLang main on 11 October 2026, separates health routing and load-budget bookkeeping from user dispatch.

02

Estimate before the full-node test

Extended an InferFlux-based capacity model for long-context inference and used workload, compute/bandwidth limits, cache memory, parallel layout, and efficiency priors to narrow the test space. For Kimi K3, examined DCP and the capacity/rollback boundaries of KV and SSM state pools.

The output is a capacity estimate, not a guaranteed throughput number. Gaps between prediction and measurement help prioritize memory, communication, batching, or runtime investigation.

03

Parallelism is a workload decision

Compared TP8/DP8 and TP8/CP8 for DeepSeek-V4-Pro, and TP8/EP8/MegaMoE and PP8 for Kimi K3. A separate GB300 CP8 V4-Pro Prefill configuration measured median TTFT of 0.666 s at 60k and 1.516 s at 128k input, with one output token.

Select hardware and parallel layout against the target workload and SLO. Compare throughput, TTFT/TPOT and resource use at the qualifying operating point.

04

EPLB: measure balance, then test throughput

Separated logical expert popularity, physical placement, replica dispatch, padding and kernel time. Earlier V4-Pro B300 work motivated a follow-up on real-token V4.1-Flash 64K/C32 Prefill workloads.

In the reported V4.1-Flash comparison, frozen placement lowered rank-count CV from 0.149 to 0.047 and average MegaMoE duration from 7.512 to 7.180 ms. Input throughput rose 0.95%, compared with 1.01% for the synthetic balanced-routing diagnostic.

Microbenchmarks and runtime profiling

Used a MegaMoE microbenchmark as a component reference for the serving trace. A 32K-chunk microbenchmark measured about 5.6 ms. In a separate V4.1-Flash real-input Prefill trace, mean main MegaMoE kernel times were 6.9–7.5 ms across ranks. Used nsys to follow execution and communication, and ncu to examine selected kernels.

Merged #43786 ↗ fuses inverse RoPE into CUDA UE8M0 FP8 activation quantization, preserving BF16 rounding and packed scales. Upstream B200 kernel tests passed 7/7, including numerical equivalence and CUDA Graph replay with updated inputs.

The microbenchmark and serving trace have different execution boundaries. The trace includes internal waits, so the gap guides attribution. The historical B300 fusion backport measured +1.61% Prefill throughput. Full-model performance of the final upstream implementation remains unmeasured.

Ascend serving engines

Worked with xLLM and vLLM-Ascend on Ascend 910B: model support, MTP, ACL Graph, cache capacity, and benchmark configuration. Qwen3.5-9B throughput moved 2,301 → 30,451 tok/s at C960 in a combined configuration comparison.

Performance → capacity → economics

Hardware selection, P/D sizing
and deployment economics

Compare serving performance, resource utilization and deployment cost under a defined SLO. Use measured phase capacity for an initial P/D allocation, then validate the combined service path.

01 / SLO

Find the feasible operating point

Sweep concurrency and configuration on the target request mix. Compare TTFT, TPOT, request throughput, memory pressure, failures, and output correctness. Select an operating point that meets the specified latency, quality, and stability criteria.

q_instance = measured requests/s
at the qualifying configuration

Prefill input tok/s, Decode output tok/s, and requests/s describe different quantities. Request lengths and phase balance must stay explicit.

02 / CAPACITY

Size Prefill and Decode separately

Convert Prefill and Decode rates to per-instance requests/s under the same workload and SLO. Size both stages for peak demand, with headroom and redundancy for the deployment.

N_P = ceil(λ_peak / q_P)
N_D = ceil(λ_peak / q_D)
Minimum GPU count = N_P × g_P + N_D × g_D

Validate the resulting P/D ratio with real KV transfers, queueing and end-to-end TTFT/TPOT. Stage-isolated rates are sizing inputs.

03 / TCO

Price delivered service

Use one accounting period for compute rental or hardware depreciation, power, networking, software, and operations. Divide by the correctly delivered token volume under the chosen service criteria. Treat input and output separately when the accounting requires it.

Cost per 1M valid tokens
= period cost / valid tokens delivered × 10⁶

Utilisation, idle reserve, uptime, retries, and traffic shape affect unit cost. Rental and depreciation require a consistent accounting boundary.

Evidence for sizing comes from benchmarks, resource limits and runtime validation. These inputs support hardware selection and comparative cost scenarios. Full TCO requires actual prices, power, utilization, redundancy, operations and delivered traffic.

Inference engineering practice

Measure the service.
Explain the bottleneck.

A repeatable loop across SGLang, NVIDIA GPUs, and Ascend: make the workload and execution path explicit, prove the result, then use it to make a resource decision.

How much correct, reliable serving capacity can this configuration deliver within its latency and resource budget?

01

Deploy & define

Pin model and framework versions, topology, request distribution, cache policy, precision, and resource limits. Confirm the intended backend and communication path.

02

Measure & profile

Separate P/D tests from end-to-end service tests. Use nsys for critical paths, CPU/GPU gaps, communication overlap, synchronisation, and graph coverage; use ncu for selected kernels.

03

Repair & validate

Test one causal hypothesis at a time. Check output quality, failure behaviour, memory boundaries, repeatability, and throughput/latency together. Carry the regression upstream.

04

Size & account

Use qualifying serving capacity for instance sizing, GPU allocation, and cost scenarios. Keep measured results, estimates, and unvalidated assumptions visible.

AI Infra is the connecting layer: model behaviour and workload shape meet runtime scheduling, cache state, kernels, interconnect, and deployment economics. My focus is building and validating that connection.
